# setup-floci

## Goal
Local dev for `oops-api-v1` connects to Postgres and Redis provisioned through Floci's RDS and ElastiCache emulation (instead of the direct `postgres:16-alpine`/`redis:7-alpine` compose services), plus S3 emulation is available for the Phase 2 attachments feature (PRD §12: prod uses RDS PostgreSQL + ElastiCache Redis + S3). Provisioning is done via Terraform targeting Floci's endpoint. `DATABASE_DSN`/`REDIS_ADDR` are hardcoded in `.env.example`/`.env.development` (confirmed deterministic — see step 14) rather than synced from `terraform output` by a script — no moving part to maintain for a value that never actually changes. Starting containers (`docker-up`) and provisioning infra (`infra-apply`) are separate steps, not one command with a hidden side effect. CI is unaffected.

Done when:
- ✅ The spike produced a **GO** verdict (2026-09-02) — see Open questions below for full findings. RDS, S3, and ElastiCache all recover automatically from a Floci restart or container recreation with `FLOCI_STORAGE_MODE=persistent`, **provided the ElastiCache replication group has cluster mode enabled** (even with a single shard, no replicas) — a plain (non-cluster-mode) group does not recover and was the initial (wrong) config tested. No workaround/repair target needed
- `oops-infra-v1/docker/dev/compose.yaml` runs Floci as a service (with `/var/run/docker.sock` mounted, and the `7001-7099`/`6379-6399` port ranges published)
- `oops-infra-v1/terraform/local/` provisions one RDS Postgres instance, one ElastiCache Redis **replication group with cluster mode enabled** (`num_node_groups = 1`, `replicas_per_node_group = 0` — not `aws_elasticache_cluster`, and not a plain non-cluster-mode replication group either), and one S3 bucket (`force_destroy = true`) against the Floci endpoint, and exposes application-level outputs (`database_dsn` marked `sensitive`, `redis_addr`, `s3_bucket`, `s3_endpoint` — not raw host/port fields the shell script would need to assemble itself)
- `oops-api-v1/Makefile` has `docker-up`/`docker-down`/`docker-logs` (containers only, no provisioning side effect) plus a new `infra-apply`/`infra-destroy` pair (checks Floci is reachable, then runs Terraform against it), and a `dev-up` convenience target chaining `docker-up` → `infra-apply`
- A new ADR is recorded that **supersedes** ADR-0002 (which explicitly decided against Floci for having no consumer — now S3 has a real Phase 2 consumer and prod already runs RDS/ElastiCache, so mirroring it locally is no longer speculative)

## Constraints
- Floci replaces Postgres/Redis via RDS/ElastiCache emulation (not just additive S3) — confirmed by user despite the added complexity of AWS-API provisioning vs. a plain compose service, because it mirrors PRD §12 prod infra
- CI must not be touched — stays on native `services:` blocks (ADR-0002 reasoning still holds: avoids Docker-socket-in-Docker on CI runners and provisioning overhead)
- `oops-infra-v1/docker/test/compose.yaml` must not be touched — stays in parity with CI
- Terraform structure is local-only for now — no premature module sharing with a not-yet-designed prod environment
- Scope is `oops-api-v1` only — no design work for `oops-agent-v1`
- Must confirm real port/auth behavior via a live spike before finalizing Terraform resources or app config — do not trust the Floci docs' RDS/ElastiCache sections at face value (they don't document data-plane ports, and ElastiCache's SigV4/IAM-auth requirement is a real risk to standard Redis clients)
- `docker-up` must never have Terraform provisioning as a hidden side effect — provisioning is a separate, explicit `infra-apply` target
- `infra-apply` must check Floci is reachable before running Terraform and fail with a clear message ("Floci is not reachable — run `make docker-up` first") instead of a raw Terraform connection error. It must not auto-start Floci itself — that stays `docker-up`'s job
- `oops-infra-v1/terraform/local/` must hardcode its AWS provider `endpoints{}` block to Floci's local address and use dummy credentials (`access_key = "test"` etc., `skip_credentials_validation = true`) — it must be structurally incapable of resolving to real AWS, not just "remember not to point it there"
- `DATABASE_DSN`/`REDIS_ADDR` are hardcoded in `.env.example`/`.env.development`, not synced from `terraform output` by a script — this was tried first (see step 10) and removed (see step 14) once repeated testing showed the endpoint never actually varies for this single-RDS-instance/single-ElastiCache-group setup. If a second RDS or ElastiCache resource is ever added to `terraform/local/`, check `terraform output` and update the hardcoded values by hand — don't reintroduce a sync script preemptively
- Persistence has different semantics per lifecycle event and must not be conflated: a Floci container restart and a compose down/up (same volumes) are expected to persist RDS/S3 *data* (subject to `FLOCI_STORAGE_MODE=persistent`); ElastiCache *service availability* also recovers automatically (cluster-mode enabled, per Floci's documented behavior) but its cache *data* does not (Floci's own docs: "caches restart empty, as on any Floci restart" — expected and acceptable, Redis here is cache/queue/pub-sub, not source of truth); a Terraform destroy/apply recreates the resources themselves, so losing data there is expected and not a bug for any of the three
- The ElastiCache resource **must** be created with cluster mode enabled (`num_node_groups = 1`, `replicas_per_node_group = 0`, `parameter_group_name` ending in `.cluster.on`) even though it's functionally a single shard from the app's point of view — this is required for Floci to reconcile/respawn the backend container on restart (confirmed via spike: a plain non-cluster-mode replication group never recovers after any Floci restart, per Floci's own docs, which document the reconciliation-on-startup behavior only for cluster-mode groups)
- Prefer running `infra-destroy` before `docker-down` when tearing down. Confirmed via spike that a *forceful* removal (`docker rm -f`/`kill`) without a prior `terraform destroy` leaks orphaned RDS/ElastiCache child Docker containers, invisible to Floci's own bookkeeping — but a *graceful* `docker compose down` (SIGTERM) cleans up its own children fine even without `infra-destroy` first (confirmed via step 12's lifecycle test). `infra-destroy` first is still the recommended order (it's the only thing that actually removes the Terraform-tracked AWS resources), just not a hard requirement for avoiding orphans specifically

## Open questions — RESOLVED (spike complete, 2026-09-02)

**Verdict: GO.** No known limitations remain — the initial "ElastiCache doesn't recover after restart" finding turned out to be a config mistake (a plain non-cluster-mode replication group), not a Floci gap. Re-reading `https://floci.io/floci/services/elasticache/` closely (at the user's prompt — good catch) surfaced the fix: cluster-mode groups are documented to reconcile on startup; non-cluster-mode ones aren't. Retested with cluster mode enabled (`num_node_groups = 1`, `replicas_per_node_group = 0`) and it recovers cleanly, same as RDS.

- ~~Data-plane port(s)~~ — RESOLVED: not the edge port. RDS gets a port from a published range `7001-7099` (`floci.services.rds.proxy-base-port`/`proxy-max-port`); ElastiCache gets a fixed port from range `6379-6399` (we set `port = 6379` explicitly in the resource and got exactly that). Both ranges must be published on the compose service (`-p 7001-7099:7001-7099 -p 6379-6399:6379-6399`), or the resources are unreachable from the host (verified: `nc` times out otherwise)
- ~~ElastiCache auth~~ — RESOLVED, and the IAM/SigV4 concern did **not** materialize: a plain unauthenticated connection works by default (raw RESP `PING` over `nc` returns `+PONG`; `go-redis/v9` with `Password: ""` connects and does SET/GET successfully). No SigV4 wrapper needed
- ~~RDS auth~~ — RESOLVED: plain username/password, no IAM needed; `pgx/v5` connects successfully with the same DSN shape as `DATABASE_DSN`
- ~~Terraform resource support~~ — RESOLVED, with two corrections to the resources originally assumed:
  - `aws_elasticache_cluster` **does not work** for Redis — Floci enforces the same validation as real AWS ("Engine must be 'memcached'. For Redis/Valkey use CreateReplicationGroup"). Must use **`aws_elasticache_replication_group`** instead
  - Its `primary_endpoint_address` attribute comes back `null` for a non-cluster-mode single-node group (a real Floci quirk); `configuration_endpoint_address` is populated correctly and must be used as a fallback (`coalesce(primary_endpoint_address, configuration_endpoint_address)`)
  - `aws_s3_bucket` needs `force_destroy = true`, or `terraform destroy` fails with `BucketNotEmpty` once any object has been written (real AWS S3 semantics, faithfully reproduced — not a bug)
  - `aws_db_instance` showed a spurious "1 changed" diff on *every* `terraform apply` (~1m20s each time) — isolated during step 9 to `publicly_accessible` (Floci's `DescribeDBInstances` always reports `false` regardless of the configured value); fixed with `lifecycle { ignore_changes = [publicly_accessible] }`, which turned it into a real no-op (~24s)
- ~~Persistence~~ — RESOLVED:
  - Default mode is `memory` — a full restart loses everything (S3 bucket disappears from `s3 ls`, RDS container left `Exited`, Redis port listens but nothing responds)
  - With `FLOCI_STORAGE_MODE=persistent` (env var, mounted volume at `/app/data`): **RDS and S3 data survive** both a `docker restart` and a full container recreate (same volume) — the RDS child Postgres container is correctly respawned by Floci on startup
  - **ElastiCache, first attempt (non-cluster-mode replication group) — did not recover**: `DescribeReplicationGroups` reported `Status: "available"` with the correct endpoint, but no Valkey container was ever respawned and the data-plane stayed unreachable, even after `describe`, `modify`, or a no-op `terraform apply`. Checked the real GitHub API (not a hallucinated web summary) to see if this was a known/fixed bug — confirmed the closed PRs that *do* touch ElastiCache restart/persistence (#398, #1268/#1403, #1607, all merged well before the `2.0.1` image tested here) don't cover this specific case
  - **ElastiCache, retested with cluster mode enabled — recovers correctly**: the user asked to re-read `https://floci.io/floci/services/elasticache/` directly before accepting the limitation, which paid off — the docs state *"cluster-mode groups are re-provisioned from their persisted topology on startup: containers are restarted, the cluster is re-formed (caches restart empty, as on any Floci restart)"*, explicitly scoped to cluster-mode groups. Recreating the group with `num_node_groups = 1, replicas_per_node_group = 0` (cluster mode enabled, still a single shard functionally) and retesting both `docker restart` and full container recreation: the `floci-valkey-*` backend container respawns automatically every time, `PING`/`go-redis/v9` reconnect with zero manual steps. Cache *data* does not survive (matches the docs — expected, and fine since Redis here is cache/queue, not source of truth), but the *service* does, same as RDS
  - `terraform destroy`/`apply` is a separate case from either of the above — expected to lose data because the resources themselves are recreated, not a bug
- No workaround/repair target needed as a result — the fix was using the right Terraform resource configuration (cluster mode enabled) from the start, not an operational workaround layered on top
